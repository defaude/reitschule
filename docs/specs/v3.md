# reitschule - Spezifikation (v3)

This latest version of the spec is deliberately reduced to an MVP scope to simplify the first implementation increment
and focus on the most critical features. We primarily  want to make recording lessons and participations of students and
horses as seamless and easy as possible for the trainers, as well as provide use-case-centric projections of the
gathered information for admins.

## Out of scope

- creation of actual compensation calculations for trainers
- cross-checking student's participation in lessons with their contracts
- any knowledge about the student's contracts / quotas

## Domain entities

- **Trainer**: Records the lessons they're hosting along with the participation of individual students and horses. May
  only use the `trainer-app` and can only see their own data. Can add arbitrary expenses in the `trainer-app`, as well.
- **Student**: Participates in the lessons, either with or without a horse.  
- **Horse**: Belongs to the school. Can be used by students when they're participating in lessons.
- **Lesson**: One riding lesson unit provided by a trainer. Can have different types (further described below). Each
  lesson type and/or trainer can have individual meanings what such a "unit" means. Depending on the type of lesson, one
  or more students can participate in the lesson.
- **Participation**: Belongs to a specific lesson entry (i.e. by a specific trainer, on a specific date & time). Each
  time a student joins a lesson unit, a "participation" record is created. This record references the lesson, the
  student and optionally a horse. No partial participation is possible; either a student participated in a lesson unit
  (or not).
- **Expense**: Any other expense that a trainer wants to get compensated for, for example when they bought a new bridle
  or lead rope that will become the school's property. Data-wise, it's a free-text description field + a currency amount
  (in EUR).

## Further refinement

- The system knows only about integer units of lessons, not about actual durations (e.g. "30 minutes").
- Which trainer gets compensated how much money per lesson unit (and type) is tracked outside of this system.
- Trainers can add/edit/remove their lessons and expenses until an admin user has marked those entries as "closed". This
  usually happens at the beginning of a month, but not at a given date, and not automatically. This "closing" is a
  manual process performed by the admin users - per trainer. This means trainer A's entries for the past month may
  already have been marked as "closed" while trainer B's entries are still editable for them.
- As noted before, admins can close a trainer's entries. Once this is done, those entries are read-only for trainers,
  but can still be edited (amended) by admins.
- All actions performed by any user (trainers and admins) are written into an audit log, which can not be tampered with.
  The only changes possible to audit log entries are related to redacting PII from those entries.

## Use-cases

The following use-cases are defined by who is performing the action, what's the intent and the desired outcome

### Add / edit / remove lesson entries

- **Who**: Trainer
- **Where**: `trainer-app`
- **Intent**: Trainers want to be compensated for each individual lesson given, so they're tracking the lesson units 
  they're giving in the system. While doing that, they also track the participation of each student and horse.
- **Desired outcome**: The system has a complete record of all lesson entries given by each trainer, so that the school
  can easily calculate the compensation for each trainer monthly. All student participation is tracked, utilization of
  all horses is tracked, as well.

### Add / edit / remove expenses

- **Who**: Trainer
- **Where**: `trainer-app`
- **Intent**: Trainers sometimes have additional expenses which benefit the school and its students and horses. These
  expenses are entered simply as a free-text description of the expense and an amount (in EUR). Trainers want to get
  refunded for those expenses with their monthly compensation.
- **Desired outcome**: The system has a complete record of all expenses spent by each trainer, so that the school can
  easily calculate the amount that needs to be refunded monthly. The descriptive text is treated as-is, no domain
  checking or inference applies.

### Amend lesson entries

- **Who**: Admin
- **Where**: `admin-app`
- **Intent**: When the data stored in the system is incorrect (even after the entries have been marked as "closed"
  already), admins can add / edit / remove lesson entries, student participation and horse utilization.
- **Desired outcome**: The entries are updated with the new information given by the admin. A log entry is written
  describing the change, including the old values which have been overwritten by the admin.

### See trainer compensation breakdown

- **Who**: Admin
- **Where**: `admin-app`
- **Intent**: At the beginning of each month, admins want to close the previous month's entries, and calculate the
  compensation and expense refunds for each trainer. For this, a dedicated view (projection) of the information stored
  in the system is needed. A tabular view with usual controls provides all the information the admin needs. The
  displayed information can be filtered by a data range, and by the trainer's name, for example.
- **Desired outcome**: The admins can quickly get an overview of the relevant information needed for the individual
  trainer's compensation / refunds.

### See student participation breakdown

- **Who**: Admin
- **Where**: `admin-app`
- **Intent**: Usually at the beginning of each month, but basically at any given time, admins want to check the
  participation of each student against their individual contracts, so that potential over- or under-usage can be
  discussed with the student. For this, a dedicated view (projection) of the information stored in the system is needed.
  A tabular view with usual controls provides all the information the admin needs. The displayed information can be
  filtered by a data range, and by the student's name, for example.
- **Desired outcome**: The admins can quickly get an overview of the relevant information needed for handling each
  individual student.

### See horse utilization breakdown

- **Who**: Admin
- **Where**: `admin-app`
- **Intent**: Usually at the beginning of each month, but basically at any given time, admins want to check how each of
  the school's horses is utilized in lessons, and by which student(s). Horses should normally only be used for a single
  lesson unit per day, though exceptions do exist. Ideally, admins should be able to track each horse's utilization so
  that they can better steer which horse is used in upcoming lessons - and which one is not. For this, a dedicated view
  (projection) of the information stored in the system is needed. A tabular view with usual controls provides all the
  information the admin needs. The displayed information can be filtered by a data range, and by the horse's name, for
  example. If a horse has been utilized in more than one lesson in any given day, those entries should be highlighted.
- **Desired outcome**: The admins can quickly get an overview of the relevant information needed for controlling each
  individual school horse. Additional to the tabular view, the `admin-app` should show a notification / warning in a
  global banner (or similar UI component), when a horse has been over-utilized on any given day. Those banners can be
  acknowledged (i.e. closed) by the user. The information whether a banner has been closed does not need to be persisted
  in the backend; a purely frontend-based persistence (e.g. with `localStorage`) is sufficient.
